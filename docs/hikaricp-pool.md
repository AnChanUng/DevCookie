# HikariCP 커넥션 풀 병목과 API 성능 개선

## 상황

로그인 직후에는 브라우저에 쌓인 문제집 기록 수십 개가 한꺼번에 서버로 동기화됩니다(`PUT /api/v1/exam/progress/{문제집}`). 이 요청이 몰리면 DB 커넥션 풀(HikariCP, 10개)이 가득 차서 동기화와 관계없는 조회 API까지 느려졌습니다.

## 원인 분석

부하 중 `hikaricp.connections.active · pending · acquire`를 1초마다 읽었습니다.

- 풀 10개가 측정 내내 모두 사용 중이었고, 커넥션을 기다리는 요청이 평균 160개(최대 190개)였습니다. 190은 Tomcat 스레드 200개에서 커넥션을 쥔 10개를 뺀 값으로, 모든 요청 스레드가 커넥션을 기다린 상태입니다.
- 문제집 저장은 사용자 행을 `SELECT … FOR UPDATE`로 잠근 채, 등급 계산을 두 번 했습니다. 등급 계산은 그 사용자의 모든 문제집 JSON(최대 200KB씩)을 불러와 매번 파싱했습니다. 문제집 30개를 동시에 저장하면 같은 계산을 60번 하는 셈입니다.
- 같은 사용자의 다른 저장 요청은 행 잠금을 기다리는 동안에도 커넥션을 쥐고 있었습니다. 잠금을 기다리는 요청이 풀을 차지해서 다른 API가 커넥션을 얻지 못했습니다.
- Open-Session-In-View(OSIV)가 기본값(켜짐)이라 요청이 끝날 때까지 영속성 컨텍스트가 열려 있었습니다.
- 2초 누수 감지(`leak-detection-threshold`)에는 걸리지 않았습니다. 커넥션 하나를 오래 쥐는 누수가 아니라, 짧게 쥐는 요청이 너무 많이 몰린 문제였습니다.

## 변경 (단계별로 측정)

| 단계 | 변경 |
| --- | --- |
| 1 | 문제집마다 푼 문제 수(`exam_progress.solved_count`)를 저장하고, 등급 계산은 `SUM` 쿼리 하나로 처리합니다. 값이 없는 예전 행은 처음 저장할 때 한 번만 채웁니다. |
| 2 | `spring.jpa.open-in-view: false`. 지연 로딩이 끊긴 문제 조회는 `@EntityGraph(attributePaths = "category")`로 과목을 함께 가져옵니다(N+1도 함께 제거). |
| 3 | 저장 트랜잭션을 컨트롤러에서 `ExamProgressService`로 옮기고, 같은 사용자의 저장은 커넥션을 얻기 전에 애플리케이션 안(사용자 ID로 나눈 잠금 64개)에서 줄을 세웁니다. 차례가 오면 짧은 트랜잭션만 엽니다. 여러 서버로 늘어날 때를 위해 트랜잭션 안의 행 잠금은 그대로 둡니다. |

## 측정

`load-tests/progress-sync.js`(k6 v2.4.0). 로그인 사용자 N명이 문제집 30개(각 120문제 풀이 기록)를 한꺼번에 저장하기를 반복하는 동안, 방문자 40명이 문제 목록·순위·채팅·과목을 조회합니다. 60초 동안 실행하고 매번 새 DB에 시드를 넣었습니다. 로컬 PC(28스레드), PostgreSQL 16(Docker), JVM 힙 1GB, 풀 10개 기준이며 운영 사용자 수를 뜻하지 않습니다.

### 30명 동시 동기화

| 항목 | 수정 전 (2회) | 1단계 | 2단계 | 3단계 (2회) |
| --- | --- | --- | --- | --- |
| 동기화 p95 | 1,066 / 1,141ms | 454ms | 469ms | **323 / 407ms** |
| 일반 조회 p95 | 976 / 1,082ms | 390ms | 1,227ms | **99 / 111ms** |
| 일반 조회 p99 | 1,442 / 1,592ms | 1,247ms | 3,321ms | **201 / 788ms** |
| 커넥션 대기 요청 평균 | 160 / 159개 | 110개 | 110개 | **16 / 23개** |
| 커넥션 획득 최대 시간 | 2,255 / 2,207ms | 2,679ms | 3,890ms | 1,071 / 2,996ms |
| 처리한 동기화 요청 | 10,590 / 9,990건 | 22,140건 | 23,910건 | **28,440 / 26,760건** |
| 처리한 조회 요청 | 3,544 / 3,364건 | 8,012건 | 5,392건 | **15,324 / 14,068건** |
| 실패 요청 | 0건 | 0건 | 0건 | 0건 |

2단계(OSIV만 끈 상태)는 오히려 조회가 느려졌습니다. 잠금을 기다리는 저장 요청이 여전히 커넥션을 쥐고 있는 상태에서, 조회 요청이 저장소 호출마다 커넥션을 다시 얻어야 했기 때문으로 보입니다. 3단계에서 기다리는 동안 커넥션을 쥐지 않게 한 뒤에야 조회가 정상으로 돌아왔습니다.

### 80명 동시 동기화 (과부하)

| 항목 | 수정 전 | 3단계 |
| --- | --- | --- |
| 동기화 p95 | 2,554ms | 1,290ms |
| 일반 조회 p95 | 2,504ms | 836ms |
| 커넥션 대기 요청 평균 | 186개 | 78개 |
| 커넥션 획득 최대 시간 | 4,881ms | 2,036ms |

80명에서는 3단계 이후에도 대기 요청이 쌓입니다. 다음 개선 후보는 문제집 기록 여러 개를 한 요청으로 묶어 보내는 일괄 저장 API입니다.

### 타임아웃

어느 실행에서도 커넥션 획득 타임아웃(HikariCP 기본 30초)이나 실패 요청은 없었습니다. 병목은 실패가 아니라 대기 시간(최대 약 5초)으로 나타났습니다.

## 다시 실행하기

```bash
docker run -d --name cs-k6-pg -e POSTGRES_HOST_AUTH_METHOD=trust -e POSTGRES_DB=cs_study_k6 -p 127.0.0.1:55432:5432 postgres:16-alpine
cd backend && ./gradlew bootJar   # JDK 17~21
java -Xmx1g -jar build/libs/cs-study-backend-0.0.1-SNAPSHOT.jar --spring.profiles.active=loadtest --app.security.rate-limit-enabled=false
docker exec -i cs-k6-pg psql -U postgres -d cs_study_k6 < load-tests/seed.sql
k6 run -e USERS=30 load-tests/progress-sync.js
```

커넥션 풀 지표는 부하테스트 프로필에서만 루프백 관리 포트(`127.0.0.1:18081/actuator/metrics`)로 열립니다. 서비스 포트의 `/actuator`는 보안 필터가 계속 막고, 운영 설정은 `health`만 노출합니다.
