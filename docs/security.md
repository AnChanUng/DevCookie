# 보안과 크롤링 확인

## 어디서 확인하나요?

`/admin/cu`에서 운영 `ADMIN_KEY`를 입력한 뒤 **보안 · 크롤링** 탭을 연다. API 서버에 도착한 요청 중 자동화 도구를 표기한 User-Agent, 요청 제한 초과, 관리자 접근 거부, 민감 경로 탐색을 확인할 수 있다. IP는 공유 네트워크·VPN·프록시를 사용할 수 있고 User-Agent는 위조 가능하므로 개인 신원이나 악성 크롤러의 확정 증거로 취급하지 않는다.

첫 HTML과 정적 파일 요청은 API 서버를 거치지 않는다. Vercel 프로젝트의 Logs 및 Observability에서 제공되는 요청 경로, IP, User-Agent와 빈도를 확인해야 한다. 제공 항목과 보존 기간은 요금제·프로젝트 설정에 따라 다르다. 기존에 수집하지 않은 과거 요청이나 운영 계정 접근 권한이 없는 로그를 이 코드로 복원할 수는 없다.

## 적용한 통제

- 관리자 키 기본값을 제거했다. Render 환경 설정에 32자 이상의 무작위 `ADMIN_KEY`를 설정해야 하며, 없거나 너무 짧으면 관리자 API는 503으로 닫힌다. 값을 저장소나 채팅에 넣지 않는다.
- 문제 생성·수정·삭제, 카테고리 생성, 콘텐츠 동기화, Slack 테스트 호출을 관리자 전용으로 제한한다. 필터와 컨트롤러에서 각각 권한을 검사한다.
- IP당 1분에 전체 API 3,000회, 로그인 등 인증 POST 60회, 질문 조회 GET/HEAD 180회, 코드 실행 15회, 챗봇 POST 60회로 제한한다. 초과하면 `429`와 `Retry-After`를 반환한다. 같은 네트워크 사용자는 한 IP 예산을 공유한다.
- `/.env`, `/.git`, `/wp-*`, `/actuator*` 탐색을 차단한다.
- Vercel에 CSP, HSTS, 프레임 삽입 차단, MIME 추측 차단, Referrer-Policy와 Permissions-Policy를 적용한다. 카메라·마이크는 기존 면접 연습을 위해 본인 출처에 허용한다. 인라인 스크립트 두 개는 외부 파일로 분리해 `script-src 'self'`를 적용했다.
- robots.txt 및 X-Robots-Tag로 자동 수집과 검색 노출을 거부한다. 이는 협조하는 로봇에 대한 규칙이며 접근 제어가 아니다.

## 기록과 한계

`security_events`에 시각, IP, User-Agent, 메서드, 쿼리를 제외한 경로, 사유, 차단 코드와 분당 요청 수를 저장한다. 인증 헤더·관리자 키·비밀번호·요청 본문은 기록하지 않는다. 같은 IP와 사유는 분당 한 번, 서버 전체 분당 최대 60개 표본으로 제한한다. 최근 7일·최신 200건만 관리자에게 제공하며 매시간 7일 초과 또는 최신 2,000개 밖의 DB 기록을 정리한다. 일반 사용자에게는 노출하지 않는다.

기본적으로 클라이언트가 보낸 X-Forwarded-For를 신뢰하지 않는다. Render의 `RENDER=true` 환경에서는 프록시가 오른쪽에 추가하는 마지막 주소를 사용한다. 추가 프록시를 두면 그 배치의 신뢰 체인에 맞춰 검토해야 하며, `TRUST_FORWARDED_FOR=false`로 명시적으로 끌 수 있다. 요청 제한은 서버 인스턴스별 메모리에 유지되므로 재시작 시 초기화되며 여러 인스턴스에서 합산되지 않는다.

공개 화면과 프론트엔드 번들로 제공되는 문제는 열람 가능한 사람이 저장할 수 있다. 분산 IP 수집과 네트워크 대역폭 공격을 이 필터만으로 막을 수는 없다. 필요하면 Vercel Firewall과 호스팅 제공자의 WAF·접근 정책을 운영 계정에서 추가한다. 이 작업에서는 운영 대시보드의 WAF 설정을 변경하지 않았다.

## 검증

backend에서 `bash gradlew test bootJar`. 관리자 보호, 429·재시도 헤더, CORS, 위조 전달 헤더, 시간 구간별 예산, 민감 경로 차단과 기록의 쿼리 제외를 테스트한다. 기존 기능 테스트에서는 제한을 끄고 보안 통합 테스트에서 활성화해 별도 H2 DB로 검증한다. 운영 DB 테이블은 새 백엔드 시작 때 생성된다.
