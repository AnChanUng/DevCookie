# 실시간 대결 동시성 제어와 결과 정합성

## 문제

| 구분 | 이전 동작 | 결과 |
| --- | --- | --- |
| 재대결 | 잠금 없이 `nextCode`가 비었는지 확인한 뒤 새 방을 만들고 저장 | 동시에 누른 요청이 모두 빈 값을 보고 각자 방을 만듦. 나중에 저장한 쪽이 `nextCode`를 덮어써서 사람들이 서로 다른 방으로 흩어짐 |
| 방 만들기 | 요청마다 새 방 생성 | 응답을 못 받고 다시 누르면(무료 서버 콜드 스타트 등) 방이 여러 개 생김 |
| 점수 | 클라이언트가 계산한 `score`·`marks`를 그대로 저장 | 요청을 고쳐 보내면 점수를 꾸밀 수 있음 |

## 변경

- **재대결 원자성:** `DuelService.rematch`가 하나의 트랜잭션 안에서 앞 방 행을 `SELECT … FOR UPDATE`(비관적 잠금)로 잠근 뒤 `nextCode`를 확인하고 다음 방을 만듭니다. 동시에 들어온 요청은 잠금에서 차례를 기다렸다가 이미 정해진 방 번호를 받습니다.
- **방 만들기 멱등성:** `POST /api/v1/duels`가 `Idempotency-Key` 헤더를 받습니다. 키는 `duels.create_key`의 유일 제약으로 지키고, 키 확인과 저장 사이에 같은 키가 끼어들면 먼저 저장된 방을 다시 읽어 돌려줍니다. 프런트는 같은 과목·같은 방식으로 다시 누를 때 같은 키와 문제를 보냅니다.
- **결과 중복 반영 방지:** 진행 상황 저장은 방 행 잠금 아래에서 (방, 방문자) 한 줄을 갱신하고, 끝낸 기록은 다시 고치지 않습니다.
- **서버 채점:** 클라이언트는 고른 보기 번호(`picks`)만 보냅니다. 서버가 정답표 `duel-bank.json`(문제 번호·정답 번호·보기 수, `frontend/scripts/export-duel-bank.mjs`로 생성)으로 맞힌 수와 정오답을 계산합니다. 클라이언트가 보낸 `score`·`marks`는 쓰지 않습니다. 정답표에 없는 문제로는 방을 만들 수 없습니다.
- **시간 검증:** 걸린 시간은 서버가 처음 진행 상황을 받은 뒤 지켜본 시간보다 짧게 줄일 수 없고, 앞서 올린 시간보다 줄어들지도 않습니다.

## 검증

모든 측정은 로컬 PC에서 Testcontainers로 띄운 PostgreSQL 16과 Spring Boot(HikariCP 기본 풀 10개)로 했습니다. 운영 사용자 데이터가 아니라 같은 조건에서 수정 전 코드와 후 코드를 비교한 결과입니다.

### 동시 요청 100건 (`DuelConcurrencyTest`, 평소 테스트에 포함)

| 시나리오 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 같은 방에서 동시에 재대결 100건 | 다음 방 10개 생성(중복 9개), 3회 모두 같음 | 다음 방 1개(중복 0개) |
| 같은 `Idempotency-Key`로 방 만들기 100건 | 방 100개(중복 99개) | 방 1개(중복 0개) |
| 같은 사람이 마지막 답안 100건 동시 전송 | — | 기록 1줄, 전적 반영 1건 |

수정 전 재대결이 매번 정확히 10개였던 것은 커넥션 풀 크기(10)만큼의 트랜잭션이 동시에 `nextCode`를 비어 있다고 읽었기 때문으로 보입니다.

### 재대결 매칭 (`DuelRematchBenchmarkTest`, `DUEL_BENCHMARK=1`일 때만 실행)

대결을 끝낸 두 사람이 동시에 "한 판 더"를 누르는 상황 500쌍을 25쌍씩 동시에 진행했습니다. 두 사람이 같은 다음 방을 받으면 매칭 성공입니다. 지연은 재대결 요청 1,000건의 응답 시간입니다.

| 회차 | 수정 전 매칭률 | 수정 전 p95 | 수정 후 매칭률 | 수정 후 p95 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 17.8% | 68.2ms | 100% | 49.2ms |
| 2 | 28.6% | 56.5ms | 100% | 52.7ms |
| 3 | 24.4% | 69.0ms | 100% | 50.5ms |
| 평균 | 23.6% | 64.6ms | 100% | 50.8ms |

수정 후에는 두 번째 요청이 방을 새로 만들지 않고 잠금이 풀리기를 기다렸다가 이미 정해진 방 번호만 읽으므로, 방 생성이 겹치던 수정 전보다 지연도 줄었습니다.

## 다시 실행하기

```bash
cd backend
./gradlew test --tests '*DuelConcurrencyTest' -i | grep -E '\[(rematch|create|report)\]'
DUEL_BENCHMARK=1 ./gradlew test --tests '*DuelRematchBenchmarkTest' -i | grep rematch-bench
```

Docker가 필요합니다. Docker Engine 29 이상에서는 `src/test/resources/docker-java.properties`가 API 버전을 1.44로 맞춥니다. Gradle 8.7은 JDK 17~21에서 실행해야 합니다. 문제은행을 고친 뒤에는 `node --import ./scripts/extensionless-loader.mjs scripts/export-duel-bank.mjs`로 정답표를 다시 만들고, `npm run check:duel-bank`로 최신인지 확인합니다.
