# 부하테스트는 어떻게 하고, 결과는 어떻게 볼까?

부하테스트의 목적은 높은 숫자를 만드는 것이 아니라, 예상한 이용량에서 서비스가 목표 응답시간과 오류율을 지키는지 확인하고 한계에 도달한 원인을 찾는 것이다.

## 실무에서 진행하는 순서

1. 목표와 실제 이용 패턴을 정한다. 예를 들어 동시 사용자 100명 또는 초당 100개 요청에서 p95 500ms 이하, 오류율 1% 미만을 목표로 삼는다. 수치는 업무 요구에 맞게 정한다.
2. 운영과 비슷한 개발/스테이징 환경과 가상 데이터를 준비한다. 서버 사양, DB 크기, 인덱스, 캐시, 네트워크 조건을 기록한다.
3. 로그인, 검색, 조회, 저장처럼 실제 행동을 조합한다. 조회만 몰아치는 테스트와 회원 인증이나 쓰기 테스트는 목적을 나눠 측정한다.
4. 작은 부하로 응답을 검증하고 부하를 단계적으로 높인다. 예상 이용량 검증(load), 한계 확인(stress), 급증 대응(spike), 장시간 누수와 성능 저하 확인(soak)을 구분한다.
5. k6와 서버/DB 지표를 같은 시간대에 관찰한다. 느린 쿼리, 커넥션 대기, CPU, 메모리/GC, 스레드 대기 등을 확인한다.
6. 병목을 개선하고 같은 조건에서 다시 측정한다. 변경 전후 수치를 비교하고 코드 버전, 데이터, 부하 조건과 원본 결과를 남긴다.

## 무엇을 확인하나?

| 보는 곳 | 주요 지표 | 확인할 질문 |
| --- | --- | --- |
| k6 | 가상 사용자, 요청/초, p95/p99, 실패율, 응답 내용 검사 | 부하가 늘어도 목표 응답시간과 정확성을 지키나? |
| 서버 | CPU, 메모리, GC, HTTP 작업 스레드, 대기 요청 | 처리 자원이 포화되거나 요청이 쌓이나? |
| DB | 쿼리 지연, 잠금, 커넥션 풀 사용/대기, 실행 계획 | 느린 쿼리나 커넥션/잠금 대기가 응답 지연과 겹치나? |
| 로그/APM | 오류, 요청별 추적, 외부 서비스 호출 시간 | 어느 처리 단계에서 시간이 소요되나? |

일반적으로 k6 대시보드는 요청을 보내는 쪽의 결과를 보여준다. 서버와 DB 내부 지표는 별도 모니터링을 함께 본다. Spring Boot 서비스에서는 Actuator/Micrometer + Prometheus + Grafana 또는 사용하는 APM을 연결하는 방식이 흔하다. 이 저장소의 이번 그래프에는 해당 모니터링을 새로 연결하지 않았으므로 DB 병목을 확정하는 자료로 사용할 수 없다.

## 그래프를 읽는 순서

1. VUs 그래프로 사용자 수가 계획대로 증가했는지 본다.
2. 요청/초 그래프에서 처리량이 증가하는지 본다. 사용자만 늘고 처리량이 더 늘지 않으면 포화 여부를 조사한다.
3. 응답시간 그래프의 p95/p99가 같은 시간에 상승하는지 본다. 평균만으로 일부 사용자의 느린 응답을 놓치지 않는다. p95가 500ms라는 것은 측정 요청의 95%가 500ms 이내라는 뜻이다.
4. HTTP 실패와 응답 검사 실패를 본다. HTTP 200이어도 잘못된 응답이면 실패로 취급해야 한다.
5. 지연과 실패가 발생한 시간대를 서버/DB 지표와 대조한다. HTTP 429는 요청 제한 정책에 따른 차단인지 확인하고 서버 처리 오류와 구분한다.

## 이번 결과와 다음 단계

현재 시나리오는 최대 100 VU가 API 8개를 순서대로 호출한 뒤 1초 쉬는 방식이다. VU는 실제 사용자나 MAU/DAU가 아니다. 이 방식은 응답이 느려지면 VU의 다음 요청도 늦어져 요청/초가 줄어든다. 정해진 초당 요청량을 견뎌야 하는 요구사항은 `constant-arrival-rate` 또는 `ramping-arrival-rate` 시나리오로 별도 검증하는 편이 맞다.

이번 측정은 로컬 PostgreSQL 가상 데이터에서의 API 검증이며 브라우저 로딩, 인터넷 지연, Render 운영 사양, 로그인 해싱과 SSE 장기 연결은 포함하지 않는다. 그 항목과 장시간 부하는 다음 테스트 범위로 구분한다.
